# Deep dive 2026-11-07: совместимость, ternary, I/O, GPU, продукт

Материал подготовлен пятью параллельными исследованиями по текущему состоянию
проекта: APK на `external/llama-clover-src` (llama.cpp PR #31306 @ `4838ffb`),
устройство MI 8 (SDM845, 6 GB, Android 15), уже полученные замеры.

Обозначения: **факт** — проверено по коду/устройству/источнику; **гипотеза** —
оценка, требует замера.

## 1. Какие GGUF реально запускаются

### Короткий ответ

Почти все **стандартные текстовые** GGUF, которые знает это дерево llama.cpp:
Llama 2/3.x, Qwen2/2.5/3, Gemma 2/3, Mistral/Mixtral, Phi, DeepSeek, Command-R,
OLMoE, DBRX, Falcon, Mamba/Jamba, BitNet и десятки других. Но это **не «любой
.gguf»**:

- архитектуры, добавленные в mainline **после** 4838ffb, APK не знает;
- новые типы тензоров (например `F8_E4M3`) APK не знает;
- vision/audio требуют `mmproj`/`mtmd`, которого в APK нет;
- огромные dense/MoE модели загрузятся, но будут читаться с UFS;
- ошибки загрузки сейчас теряются: UI показывает только `engine load failed`.

### Дерево 4838ffb

- 167 архитектур `LLM_ARCH_*`; 165 имеют mapping/класс, без реализации остались
  `GPTJ` и `UNKNOWN`.
- `clover_moe`支持 нативно, без патчей проекта; в 4838ffb читаются
  block-diffusion тензоры (`ssm_bd_*`), которых нет в mainline.
- Кванты: Q2_K–Q6_K, Q8_0, IQ1_S/M–IQ4_XS, TQ1_0/TQ2_0, BF16/F16/F32,
  MXFP4/NVFP4, Q1_0/Q2_0. Q8_K/Q8_1 — промежуточные.
- Токенайзеры: SPM, BPE, WPM, UGM, RWKV, PLaMo2/3 — почти не блокер.

### Чего нет по сравнению с mainline f7591a6

- 6 новых архитектур: `xing4_0`, `metis16`, `mistral-large4`, `kimi-k31`,
  `limite`, `ricursive`.
- Новый тип `F8_E4M3` (id 43). GGUF, сделанный новым квантователем, APK не откроет.
- Соответственно, «скачал самый свежий GGUF с HF» — не гарантия.

## 2. Тернарные модели

### Что уже есть

- `GGML_TYPE_TQ1_0=34`, `TQ2_0=35`; блоки 54/66 байт на 256 весов
  (1.69/2.06 bpw).
- Dequant + `vec_dot` для CPU, включая ARM NEON **без dotprod** через `vmlal_s8`.
  Это не «только сдвиги»: активации квантуются в `q8_K`, идёт int8 multiply-accumulate.
- Repack для TQ **нет**; `nrows=1` — prefill страдает.
- `llama-quantize --TQ1_0/--TQ2_0` есть, но `quantize_tq*` **игнорирует imatrix**
  и делает `lround(x/absmax)` без группы/порога. Обычную модель переквантовывать
  нельзя — будет мусор.
- Загрузчик `bitnet` есть, но в графе используется **SiLU**, а официальная
  BitNet b1.58 2B4T обучена с **relu2**. PR #26751 (relu2) закрыт без мержа.
  Без патча качество BitNet невалидно.
- Официальный `microsoft/bitnet-b1.58-2B-4T-gguf` не грузится: arch
  `bitnet-b1.58` (в дереве только `bitnet`) и тип тензоров 36 (в llama.cpp это
  удалённый тип). Falcon3-1.58bit GGUF — та же история.
- Vulkan-путь для TQ в дереве есть, OpenCL — нет. APK CPU-only, значит на 845
  только CPU.

### Рабочий кандидат для bring-up

`ewchampion/Ternary-Bonsai-1.7B-TQ2_0-GGUF`: 624.6 MB, Apache-2.0, arch `qwen3`,
196 тензоров TQ2_0, Q6_K embed, F32. Проверен по заголовку. Должен загрузиться
без патчей. Гипотеза: decode 13–18 tok/s, prefill 12–18 tok/s на 4×A75.

BitNet-кандидат `ihtesham0345/bitnet-b1.58-2B-4T-llamakind` (1.106 GB, TQ1_0)
загрузится, но без патча relu2 качество будет «связным, но неправильным».

### Что это даст на 845

Смысл TQ — **качество 1.5–2B при скорости 0.5B**, а не абсолютная скорость.
Оценки: Bonsai 1.7B TQ2_0 — 13–18 tok/s decode, 12–18 prefill; BitNet 2B TQ1_0 —
9–16 tok/s; 2k промпт — 2–3 минуты TTFT. Для длинного system prompt/RAG тернарник
плох. Для коротких диалогов — интересен.

### План интеграции

1. Патч `relu2` в `src/models/bitnet.cpp` + `llama-model.cpp` (5 строк) для BitNet.
2. Скачать Bonsai 1.7B TQ2_0 и BitNet TQ1_0; pre-flight парсер GGUF.
3. Desktop CLI → device CLI → JNI (загрузка уже работает).
4. Вернуть в `nativeInfo` `ftype`, `quant`, `is_ternary` через `llama_model_ftype()`.
5. В `GgufMeta` читать tensor infos и считать типы 34/35/42; в UI — бейдж
   `TERNARY` и предупреждение о качестве.
6. Quality gate 22 промпта против Qwen2.5-0.5B / Qwen3-1.7B Q4.
7. Не добавлять квантайзер на устройство.

## 3. Устройство, эксперты и I/O

### Главное открытие: `expert-profile.bin` — не Clover

Формат `STRP` v1:

```
0x00 "STRP"
0x04 u32 version = 1
0x08 u32 n_rows = 48
0x0C u32 n_cols = 512
0x10 u32 n_cells = 24576
0x14 u32 n_cells = 24576
payload: order[24576] (u16 row, u16 col) + rank[24576] u32
```

Это 48×512 = 24 576 экспертов. У Clover 40×256 = 10 240. В top-5 есть строки
46, 47, 44 — они не могут быть padding’ом 40-слойной модели. Значит, файл
принадлежит другой модели (вероятно Qwen3.8-Flash-Next из 4 GB проекта).
Применять его к Clover нельзя — будет мусорный hot set. Нужен новый профиль
40×256 с роутера Clover либо онлайн-счётчики.

### Что делает llama.cpp на CPU

- `mmap` + page cache. `llama-moe-cache` — **device-кэш**: на CPU бросает
  `MoE cache requires a GPU backend`; `moe_cache_mb>0` на CPU — ошибка, не no-op.
- Загрузка с `prefetch=true` может делать `MAP_POPULATE`/`WILLNEED` на весь
  12.5 GB файл — это стоит проверить и, вероятно, отключить (E0b).
- Экспертные тензоры: `ffn_gate_exps`, `ffn_up_exps`, `ffn_down_exps`;
  суммарно 10 304 MiB, dense 1 672 MiB. Средний эксперт 1.006 MiB.
- В графе `build_moe_cache_slots` + `ggml_mul_mat_id` уже поддерживают slot map;
  CPU-ядро понимает `id=-1`. Это можно переиспользовать для host-пула.

### Измерения на устройстве (факт)

| Тест | Результат |
| --- | ---: |
| seq read 512 MiB O_DIRECT 1 поток | **538.8 MB/s** |
| random 1 MiB O_DIRECT | **490 MB/s** (p50 1.917 ms) |
| random 4 KiB O_DIRECT | ~**4 975 IOPS** |
| token-нагрузка 360 MB, pread 1 поток | 265 MB/s |
| token-нагрузка 360 MB, pread 2 потока | 531 MB/s |
| token-нагрузка 360 MB, O_DIRECT 2 потока | **704 MB/s** |
| mmap резидентные страницы | 2.4–2.5 GB/s |
| mmap seq горячий | 8.6 GB/s |
| `MADV_WILLNEED` 64 MiB | 616 MB/s |
| page cache residency | **2.35 GiB = 19.6 % файла** |

### Бюджет 6 GB

| Статья | MiB |
| --- | ---: |
| MemTotal | 5 499 |
| Android/ядро/модем/GPU reserve | 1 300–1 450 |
| dense (output 398 + embd 273 + attn/ssm 842 + shared 148 + norms 11) | 1 672 |
| compute buffer | 127.5 |
| recurrent state | 62.8 |
| KV q8_0 ctx 4096 | ~45 |
| код/JNI/стеки | 120–180 |
| safety margin | 250–350 |
| **остаётся на экспертов (пул + page cache)** | **1 700–1 900** |

### Три дизайна

A. **Только page cache + `WILLNEED`**: 1–2 дня, без нового расхода RAM, но
   hit rate остаётся 20–30 %, fault’ы дорогие.

B. **Явный RAM-пул поверх mmap**: 24 слота/слой = 966 MiB, O_DIRECT pread,
   2 I/O потока, admission 2-hit/256 токенов, per-layer 2Q/SLRU. Детерминированная
   память, hit управляем. Основной кандидат.

C. **Гибрид**: hot set в пуле + cold через mmap + prefetch L+1 по онлайн-счётчикам.
   Лучший потенциал, но сложнее и спекуляция может вредить.

### Параметры старта

| Параметр | Значение |
| --- | --- |
| Слотов/слой | **24** (fallback 20) |
| Пул | **966 MiB** |
| Admission | 2-hit / 256 токенов |
| Eviction | per-layer 2Q/SLRU, protected 50 % |
| Prefetch | текущий слой — все misses; L+1 — top-2 только при idle |
| I/O | O_DIRECT + 4 KiB bounce, 2 потока, queue depth 4 |
| Compute | 4×A75; I/O — 2×A55, nice +10 |
| Prefill | bypass при `n_tokens > 32` |

### Прогноз

| Сценарий | Hit | Decode |
| --- | ---: | ---: |
| Оптимистичный | 60–65 % | **1.20–1.35 tok/s** |
| Реалистичный | 42–50 % | **0.95–1.10 tok/s** |
| Пессимистичный | 20–25 % | **0.70–0.80 tok/s** |

Потолок ~1.1–1.3 tok/s: даже при 100 % hit остаётся dense ~1.4 GB/токен.
Чтобы уйти выше, нужно уменьшать output head/attn/ssm или использовать спекуляцию.

### Первые эксперименты

- E0b: отключить whole-file `MAP_POPULATE`/`WILLNEED`, `FADV_RANDOM` на экспертов.
- E1: `WILLNEED` top-4 текущего слоя.
- E2: пул 16/20/24, admit-all vs 2-hit, buffered vs O_DIRECT.
- E3: гибрид + L+1 top-2 + 2 I/O потока.
- E4: 1/2/3 I/O потока, bounce 4 KiB vs 512 B.
- E5: admission 1/2/3, aging 128/256/512.

## 4. Vulkan, OpenCL, NPU

### 845: окончательный ответ

- **OpenCL**: работает, но **3.05 pp / 2.23 tg** против 41.8 / 26.6 CPU.
  Adreno-ядра не компилируются (`dot_acc_sat_4x8packed_ss_int`,
  `qcom_wave_pair_mode`). Generic-ядра в 12–14 раз медленнее.
- **Vulkan**: субагент собрал backend из 4838ffb и проверил на устройстве.
  GPU виден (`Adreno 630, fp16:0, int dot:0, matrix cores:none`), но:
  - `device Vulkan0 does not support 16-bit storage` — отказ;
  - патч fp32-only (аналог PR #27723) снимает проверку, но **SIGSEGV** в
    `ggml_vk_create_buffer`.
  Вывод: на этом драйвере Vulkan не заработает без глубокой переделки.
- **NPU**: `ggml-hexagon` собирает только v73/v75/v79/v81/v85; Hexagon 685 =
  v65 — не поддерживается. QNN/SNPE для 845 и Clover — не тратить время.

### Почему OpenCL так медленно

- Decode memory-bound: 0.37 GB / 26.6 tok/s ≈ 9.8 GB/s; LPDDR4X ~29.9 GB/s →
  потолок ~3x, реалистично 1.2–1.8x.
- OpenCL даёт ~450 ms/токен — это в 30 раз выше memory floor; 97 % времени не
  чтение весов, а launch/sync/declaration/driver overhead.
- Generic-ядра не используют Adreno-специфику; Q4_K деквантуется в f32.

### Новые устройства

| | 845 | 8 Gen 3 16 GB | 8 Elite 24 GB |
| --- | --- | --- | --- |
| CPU | 26.6 / 41.8 (факт) | мерить | мерить |
| OpenCL | 2.23 / 3.05 (факт) | 1.5B: 24.1 / 252; 3B: 21.4 / 136 (лит.) | 1B: ~22 / 199–275 (лит.) |
| Vulkan | не работает | работает с патчами, драйвер падает | vendor abort; Turnip |
| Prefill | GPU не помогает | **2–5x** | **3–6x** |
| Decode | GPU хуже | около CPU | около CPU / NPU |
| Clover | 0.6 tok/s, I/O-bound | 16 GB на грани | 24 GB комфортно |
| Действие | CPU 4T | CPU, потом OpenCL/NPU | CPU, NPU, потом Vulkan |

### CPU-резерв на 845

- Repack фактически **не активируется**: `GGML_CPU_REPACK=ON`, но пути
  `Q4_0_4_4/8_8` и K-repack гейтятся dotprod/i8mm, которых нет.
- Q4_0 вместо Q4_K_M может дать 10–20 % decode — **надо измерить**.
- Affinity: `taskset -c 4-7` / `--cpu-mask 0xF0 --cpu-strict 1` — **надо измерить**.
- Prefill chunk 256/128 — **надо измерить**.
- KV q8_0 уже стоит; q4_0 — только для длинного ctx.
- FP16 не включать: +1 % pp / −3 % tg.
- Speculative decoding на memory-bound 845 — не приоритет.

## 5. Продуктовый аудит: что чинить до новых фич

### P0 — надёжность

1. **Гонка `selectModel`**: нет single-flight; два тапа → два `nativeLoad`,
   возможен UAF/утечка 12 GB.
2. **`Stop` под мьютексом**: `nativeCancel` ждёт lock, который держит prefill
   до 26 с → ANR. Нужен atomic cancel и проверка внутри prefill.
3. **`nativeTrim` при 60 во время генерации** чистит KV, decode продолжает
   писать с позиции 0 → порча контекста.
4. **Нет foreground service**: экран погас/фон → генерация умирает.
5. **`engine.free()` на main** в `unloadModel`/`updateConfig` — ANR на размапливании.
6. **Импорт**: нет `.part`, `StatFs`, SHA, отмены, фильтра `.gguf`; обрыв →
   битый файл в списке.
7. **`GgufMeta.readString`** читает до 1 GB в `ByteArray` — OOM на крафченом GGUF.
8. **COMPLETE-трим** чистит native-историю, UI-список остаётся → тихая потеря.
9. **Логи** одним `Text` на 200k символов + `EXTRA_TEXT` → джанк/Binder-лимит.
10. **`config.json`** перекрывает Tuning при каждом старте.

### P1 — UX и архитектура

- история чатов (JSONL) и автосейв;
- copy/regenerate/edit/search, markdown;
- удаление моделей, SHA, свободное место, профили `model+device`;
- предупреждение «ctx 32K на 6 GB» и «threads 8 медленнее 4»;
- онбординг и человеческие ошибки (ENOSPC/OOM/LMK/bad GGUF);
- `GenerationService` с прогрессом/Stop;
- разделение mainline/Clover сборок для будущего `mtmd`.

### Мультимодальность

**Пакеты способностей**, не один комбайн:

```
core/        EngineGate, ModelRuntime, JobQueue
text/        llama.cpp mainline + Qwen3-0.6/1.7B
vision-in/   libmtmd + mmproj + SmolVLM-500M / Qwen2.5-VL-3B
image-gen/   stable-diffusion.cpp + SD1.5 Q4 (Studio; 845 — demo)
audio-in/    whisper.cpp tiny/base
audio-out/   Android TTS
video-in/    MediaCodec → 8–16 кадров → VLM
```

На 6 GB одновременно один тяжёлый движок; mmproj/whisper/SD грузить лениво и
выгружать по таймеру/`onTrimMemory`.

## 6. Рекомендуемый следующий вектор

Если цель — «дико оптимизированное приложение под Snapdragon», порядок такой:

1. **P0-надёжность** (single-flight, cancel, trim, foreground service, импорт,
   сохранение чатов) — без этого новые фичи опасны.
2. **Экспертный I/O для Clover** — E0b + host-пул 24/слой; ожидаемо 0.6 → 0.95–1.1 tok/s.
   Сначала новый профиль 40×256 или онлайн-счётчики; текущий `expert-profile.bin`
   не Clover.
3. **Ternary bring-up** — Bonsai 1.7B TQ2_0; если качество/скорость устроят,
   отдельная вкладка. BitNet — только после патча relu2.
4. **CPU-тюнинг** — Q4_0 vs Q4_K_M, affinity, prefill chunk; дешёвые проценты.
5. **Новые устройства** — 8 Gen 3/Elite: CPU baseline, OpenCL prefill, Hexagon;
   Vulkan последним.
6. **Мультимодальность** — vision-in на mainline + mtmd, затем audio, затем SD.

На 845 **не тратить время** на Vulkan/OpenCL/NPU для LLM: измерено, не работает
или медленнее. На 845 главный рычаг — I/O и page cache, не compute.
