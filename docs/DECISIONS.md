# Журнал архитектурных решений (ADR)

Формат: решение, контекст, следствия. Дата — 2026-11-07, если не указано иное.
Статусы: `accepted`, `proposed`, `superseded`.

---

## ADR-012 — Приложение полностью на Rust (supersedes ADR-002)

**Статус:** accepted (2026-11-08)

**Решение:** новое приложение пишется **полностью на Rust**. Kotlin/Compose и
C++-оболочка v0.1 удалены из проекта и перенесены в архив вне папки проекта.
llama.cpp остаётся C++-библиотекой и подключается через Rust FFI; UI — Rust
(Slint — основной кандидат, финальный выбор после исследования).

**Контекст:** пользователь явно требует Rust. ADR-002 (Kotlin/Compose + C++)
был ошибочным для этого требования; предыдущая сессия следовала ADR вместо
требования. Rust-тулчейн и Android-таргеты есть.

**Следствия:**
- никакого Kotlin в новом приложении;
- `crates/sllm-core` — UI-agnostic Rust-ядро;
- UI-фреймворк, FFI и сборка APK — отдельные решения;
- модели, документация и исследования сохранены;
- старый APK больше не является продуктом.

## ADR-001 — Единая память, три уровня доступа

**Статус:** accepted

**Решение:** считаем, что GPU, CPU и DSP делят одну RAM. «VRAM», «RAM» и «SSD» — это
уровни размещения/доступа, а не три независимых пула. Бюджет один; GPU-кэш отнимает
память у CPU и ОС.

**Контекст:** Android/Snapdragon — unified memory; в 4 GB CUDA-проекте VRAM была
отдельной, и этот опыт нельзя копировать один в один.

**Следствия:**
- планировщик считает общий бюджет, а не «свободную VRAM»;
- `onTrimMemory` — часть архитектуры, а не костыль;
- метрика `gpu_alloc_mb` — наша, драйвер её не показывает.

## ADR-002 — Нативное приложение + llama.cpp как ядро

**Статус:** accepted

**Решение:** продукт — Kotlin/Compose + C++ ядро на llama.cpp. PocketPal AI и Google AI
Edge Gallery — референсы и baseline, не основа кода.

**Контекст:** нужен контроль над mmap, экспертным кэшем, KV, потоками и логами.
Flutter + высокоуровневый биндинг это скрывает; LiteRT-LM заточен под Google-модели.

**Следствия:**
- больше работы по UI/менеджеру моделей;
- llama.cpp оборачиваем, а не форкаем на старте;
- патчи — upstream-friendly, форк только при необходимости.

## ADR-003 — Clover APEX-I-NanoPlus как первая целевая модель

**Статус:** accepted

**Решение:** первый сквозной тест — Clover 35B-A3B APEX-I-NanoPlus V2.1 (11.69 GB).
До неё — лестница маленьких моделей (0.1–10 GB).

**Контекст:** Clover — реальный MoE-сценарий, но на 845 это стресс, а не прогулка.

**Следствия:**
- bring-up начинается с tiny/small;
- Clover на 845 может остаться demo стабильности, а не скорости;
- файл модели и профиль лежат в `models/clover/`.

## ADR-004 — JSONL-логи и конфиг без переустановки

**Статус:** accepted

**Решение:** каждый запрос — строка JSON; конфиг читается из файла и меняется из
dev-консоли; «Apply» перезапускает движок, не приложение.

**Контекст:** оптимизация — это цикл «поменял → замерил → сравнил», а переустановка
убивает цикл.

**Следствия:**
- обязательные поля (модель, хеш, конфиг, thermal);
- append-only и экспорт;
- приватность: тексты промптов по умолчанию не пишутся.

## ADR-005 — Backend — runtime-параметр

**Статус:** accepted

**Решение:** `cpu / vulkan / opencl / auto` выбирается в конфиге; значение по умолчанию
для каждого устройства определяется замером, а не догмой.

**Контекст:** Adreno 630 и Adreno 830 сильно разные; OpenCL может быть быстрее Vulkan,
но незрелее.

**Следствия:**
- оба бэкенда собираются, но грузятся динамически;
- при падении GPU — откат на CPU с записью в лог;
- таблица «backend по устройству» появляется после Phase 2.

## ADR-006 — Тернарная ветка отдельная, не default

**Статус:** accepted

**Решение:** TQ1_0/TQ2_0 — отдельный режим с предупреждением о качестве; обычные модели
не переквантовываем в TQ «на лету».

**Контекст:** тернарные веса дают память и скорость, но качество ниже; корректно только
для обученных тернарных моделей.

**Следствия:**
- автоопределение по типу тензоров;
- quality gate обязателен;
- GPU-кернел для TQ — отдельная задача.

## ADR-007 — Никаких чисел до Phase 0

**Статус:** accepted

**Решение:** в документации и обещаниях нет tok/s для Android до профилирования. Места,
где нужно число, помечены TBD.

**Контекст:** перенос чисел с CUDA-ноутбука/5090 — ложь; даже между телефонами разброс
в разы.

**Следствия:**
- Phase 0 обязательна;
- каждое число имеет протокол;
- «не воспроизвелось» пишется рядом, а не затирается.

## ADR-008 — Модели вне APK

**Статус:** accepted

**Решение:** GGUF скачивается/импортируется отдельно, проверяется SHA-256; APK не
содержит больших весов.

**Контекст:** Clover 11.69 GB; Play/APK-лимиты; обновления модели не должны требовать
обновления приложения.

**Следствия:**
- менеджер моделей и докачка;
- проверка свободного места;
- scoped storage / SAF.

## ADR-010 — Оболочка: один процесс, Compose, внешние файлы

**Статус:** accepted

**Решение:** приложение — один процесс Kotlin/Compose + статически слинкованное
C++ ядро. Конфиг и логи — в app-specific external files, доступных через adb.
Цель по памяти оболочки — 50–100 MB без страниц модели.

**Контекст:** 6 GB на телефоне, LMK убивает процессы; нужен быстрый цикл
«поменял конфиг → замерил», без переустановки APK.

**Следствия:**
- минимум зависимостей (Compose, core-ktx, activity, lifecycle);
- `config.json` читается при старте, Tuning пишет в SharedPreferences;
- `session.jsonl` — во внешних files, `adb pull` работает;
- модель и page cache учитываются отдельно от heap оболочки.

## ADR-011 — Clover собирается из PR #31306 @ 4838ffb

**Статус:** accepted (временно, до исправления mainline)

**Решение:** APK линкует `external/llama-clover-src` — worktree на коммите
`4838ffb0c8ade92f34d9157deea38d92758ab824` ветки PR #31306. Mainline llama.cpp
остаётся для экспериментов и будущего ребейза.

**Контекст:** mainline `clover_moe` не читает 120 block-diffusion тензоров
(`ssm_conv1d.weight_right`, `ssm_bd_history`, `ssm_bd_logit_scale`) и выдаёт
бессвязный текст на нашем GGUF. Ветка 4838ffb использует их и даёт осмысленный
ответ; проверено на устройстве.

**Следствия:**
- ядро не обновляется автоматически вместе с mainline;
- ребейз/переход обратно — только после quality gate на том же GGUF;
- `docs/13-CLOVER.md` фиксирует, что именно проверено и какие числа получены.

## ADR-009 — Quality gate до скорости

**Статус:** accepted

**Решение:** изменение, которое ускоряет, но ломает 22-промптный gate, не считается
улучшением.

**Контекст:** опыт 4 GB проекта: кэш и квантование меняют ответы; без gate это
невоспроизводимо.

**Следствия:**
- gate встроен в релизный цикл;
- экспериментальные режимы помечаются.
