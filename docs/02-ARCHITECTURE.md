# 02 — Архитектура движка

## Принципы

1. **Один бюджет памяти.** GPU-кэш, CPU-пул и page cache делят одну RAM. Решения
   принимаются планировщиком, а не «сколько свободно в VRAM».
2. **Эксперты — это поток данных, а не модель в памяти.** Файл лежит на SSD; горячие
   эксперты — в RAM/GPU; холодные читаются по требованию.
3. **Сначала измерить, потом оптимизировать.** Каждый переключатель (backend, слоты,
   KV, prefill chunk) имеет лог и A/B.
4. **Один код — две ветки моделей.** Обычные GGUF (K/IQ-кванты) и тернарные (TQ1_0/TQ2_0)
   идут через общий планировщик, но с разными ядрами.
5. **Не тащить CUDA-решения.** Опыт 4 GB проекта — это идеи, не код: там отдельная VRAM
   и CUDA, здесь unified memory и Adreno.

## Схема

```
┌────────────────────────── Android (Kotlin, Compose) ──────────────────────────┐
│  UI чата · менеджер моделей · dev-консоль · настройки · экспорт логов         │
└───────────────────────────────────┬───────────────────────────────────────────┘
                                    │ JNI (тонкий, стабильный API)
┌───────────────────────────────────▼───────────────────────────────────────────┐
│                         C++ core (libsnapdragonllm)                           │
│                                                                               │
│  ModelLoader ── GGUF, mmap, токенайзер, chat template, SHA-256                │
│  Scheduler   ── роутер → top-k → где эксперт → вычисление → агрегация         │
│  Cache       ── профиль горячих, per-layer слоты, LRU/адмиссия, prefetch      │
│  KV          ── q8_0 / q4_0, контекст, flash attention                        │
│  Prefill     ── чанки, заимствование буферов, CPU+GPU split                   │
│  Sampler     ── temperature/top-p/top-k/penalties/seed                        │
│  MemoryGov   ── бюджет, onTrimMemory, резерв, освобождение GPU-буферов        │
│  Logging     ── JSONL на запрос, счётчики по слоям, thermal, I/O              │
│                                                                               │
│  Backends:  CPU (NEON/dotprod/i8mm) │ GPU (Vulkan/OpenCL) │ NPU (QNN, позже)  │
└───────────────────────────────────┬───────────────────────────────────────────┘
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
  GPU-видимая RAM              CPU RAM / page cache            SSD (UFS)
  горячие эксперты,            остальные эксперты,             GGUF, mmap
  dense, KV, scratch           веса, буферы
```

Верхние два уровня — **одна и та же физическая RAM**. Разница в том, кто читает и
вычисляет: Adreno через OpenCL/Vulkan-буфер или CPU через обычные указатели.

## Что где живёт

| Данные | Предпочтительное место | Почему |
| --- | --- | --- |
| Токенайзер, chat template, конфиг | RAM (маленькое) | нужно всегда |
| Dense: attention/GDN, shared expert, router | GPU (если влезает) или CPU | считается каждый токен |
| Embeddings / output head | GPU или CPU | голова может быть большой; на 6 GB — CPU/частями |
| Горячие эксперты | GPU-кэш | самый быстрый путь |
| Тёплые эксперты | RAM (CPU-пул) | без чтения с SSD |
| Холодные эксперты | SSD (mmap) | читаются по требованию |
| KV cache | RAM, при возможности GPU | растёт с контекстом; квантуется |
| Prefill scratch | RAM/GPU, временно | можно одалживать под кэш между запросами |

## Путь одного токена (decode)

1. **Embedding** токена → скрытое состояние.
2. Для каждого слоя:
   - **Норма + router** (dense): получаем top-k экспертов (у Clover k=8 из 256).
   - Для каждого выбранного эксперта:
     - **hit в GPU-кэше** → считаем на GPU;
     - **hit в RAM-пуле** → считаем на CPU (NEON);
     - **miss** → читаем blob с SSD через mmap/page cache, считаем на CPU,
       при возможности ставим в кэш.
   - **Shared expert** (dense) — всегда.
   - **Attention / GDN** — dense, GPU или CPU.
   - Агрегация выходов экспертов, residual.
3. **Final norm + head** → логиты.
4. **Sampler** → следующий токен.

Ключевая метрика — **expert hit rate** по слоям: сколько выбранных экспертов нашлось в
GPU/RAM без чтения с SSD. Именно она, а не «процент кэша», определяет скорость.

## Экспертный кэш

### Что кэшируем

Единица — **эксперт целиком** (gate/up/down одного эксперта), упакованный в один
непрерывный blob. Читать три матрицы тремя `pread` хуже, чем один блок 1–2 MB.

### Политика

- **Профиль горячих.** Офлайн-профиль (как `expert-profile.bin` в 4 GB проекте) даёт
  ранжирование пар «слой/эксперт». На старте заполняем кэш по профилю.
- **Per-layer слоты.** Каждому слою — своя квота. Без этого жадное заполнение
  «кто первый пришёл» даёт низкий hit rate (в 4 GB проекте: ~3% против 21–70%).
- **LRU/aging.** Онлайн-счётчики хитов и вытеснение по давности; профиль — начальное
  приближение, а не приговор.
- **Prefetch.** Пока считаем слой L, читаем вероятных экспертов слоя L+1. На Android это
  `mmap` + `madvise(MADV_WILLNEED)` или фоновый `pread` в пул.
- **Батчинг чтений.** Несколько miss-экспертов одного слоя читаем подряд, одним потоком
  I/O; вычисление — параллельно на big-ядрах.
- **Cache bias (опционально).** Роутер слегка предпочитает уже residency-экспертов. Это
  меняет ответы, поэтому только как эксперимент с quality gate.

### Чего не делаем

- Не держим всех экспертов в RAM «на всякий случай» — это убивает page cache и ОС.
- Не читаем эксперта с SSD, если он уже в page cache: `mmap` сам даст страницы, но
  счётчик I/O должен это видеть.
- Не кэшируем эксперта, который нужен один раз: admission по частоте.

## Dense-путь

Dense-часть (attention/GDN, shared expert, router, embeddings, head) считается каждый
токен и поэтому важнее для latency, чем редкие эксперты.

- Если dense влезает в GPU-память — держим там: это снимает с CPU самую горячую работу.
- Если нет — dense на CPU, GPU отдаём под горячих экспертов.
- **Важно:** на мобильном GPU память общая, поэтому «перенос dense на GPU» не добавляет
  пропускной способности памяти. Он помогает только там, где вычисления упираются в
  арифметику (prefill, attention), а не в чтение весов (decode).

## KV cache

- Тип: `q8_0` по умолчанию, `q4_0` на 6 GB и/или длинном контексте.
- Контекст: 2K/4K/8K/16K/32K — отдельные замеры; KV растёт линейно.
- Flash attention — если поддерживается бэкендом; иначе обычное внимание.
- KV не вытесняем в середине разговора; при нехватке памяти уменьшаем контекст или
  просим пользователя начать новый чат.

## Prefill (чтение промпта)

- Чанки 128–512 токенов; больше — больше scratch, меньше — больше накладных расходов.
- **Заимствование буферов:** между запросами scratch prefill не нужен; его можно отдать
  под экспертный кэш. В 4 GB проекте это дало +13% decode на коротком контексте — здесь
  механизм стоит проверить отдельно.
- CPU+GPU split: GPU считает dense/attention, CPU — экспертов; или наоборот, если GPU
  занят. Все комбинации — через конфиг и лог.
- На 845 prefill может быть быстрее на CPU, чем на старом Adreno; на 8 Elite — наоборот.
  Это измеряется, не угадывается.

## Decode и спекуляция

- **N-gram / repeat speculation:** если в промпте или ответе повторяется фрагмент,
  движок предлагает несколько токенов и проверяет их одним проходом. Дёшево, не требует
  draft-модели; хорошо работает на код/JSON/повторяющийся текст.
- **MTP / draft head:** если у модели есть (Qwen3.6, Ornith), используем; у Clover его нет.
- **Diffusion-блок Clover:** не используем как спекуляцию — проверка блока стоит ещё
  одного полного прохода, и в 4 GB проекте это было медленнее. Оставляем как research.
- Логируем: сколько токенов предложено, сколько принято, сколько отброшено.

## Тернарная ветка

- Форматы: **TQ1_0** (1.58 бита) и **TQ2_0** (2 бита) в ggml/llama.cpp.
- CPU-ядра тернарных квантов используют сложения/сдвиги; это хорошо ложится на мобильные
  CPU и на память (в 4–8 раз меньше весов).
- GPU-ядра для TQ в llama.cpp ограничены; для Adreno, скорее всего, потребуется свой
  OpenCL/Vulkan-кернел. Это отдельная задача, не «просто выбрать квант».
- Проверять: качество (тернарные модели заметно слабее), скорость CPU, нагрев.
- В приложении — отдельная вкладка «Ternary»; автоопределение по типу тензоров GGUF.

## Планировщик и потоки

- **Big-ядра** (A75 / A720 / Oryon) — вычисления; **little** (A55/A520) — I/O, токенайзер,
  логирование.
- Не занимать все ядра: на 845 это быстро приводит к throttling. Начинать с 4 big,
  измерять 2/4/6/8.
- Приоритеты: UI-поток не трогаем; inference — foreground service, `THREAD_PRIORITY_BACKGROUND`
  для I/O.
- GPU и CPU могут работать одновременно (dense на GPU, эксперты на CPU), но синхронизация
  стоит дорого; включать только если замер показал выигрыш.

## Отказы и деградация

| Ситуация | Поведение |
| --- | --- |
| `onTrimMemory(TRIM_MEMORY_RUNNING_LOW)` | выгрузить GPU-кэш экспертов, оставить dense и KV |
| `TRIM_MEMORY_COMPLETE` | сохранить чат, освободить всё, перезапустить движок |
| Не хватает RAM на KV | уменьшить контекст, предупредить пользователем |
| GPU-бэкенд упал | откат на CPU, запись в лог, предложить перезапуск |
| SSD медленный / miss > 90% | уменьшить кэш, увеличить prefetch, предупредить |
| Перегрев | снизить потоки/GPU, показать thermal status |

## Что пишем сами, а что берём готовым

**Берём из llama.cpp/ggml:**
- чтение GGUF, токенайзер, chat template;
- CPU-ядра (NEON, dotprod, i8mm) и K/IQ/TQ-деквант;
- Vulkan/OpenCL-ядра;
- сэмплер и базовый API генерации.

**Пишем сами:**
- экспертный планировщик: профиль, per-layer слоты, LRU/aging, prefetch;
- memory governor под Android (`onTrimMemory`, бюджет, освобождение GPU);
- слой I/O: mmap vs pread, батчинг, `madvise`;
- JSONL-логи, dev-консоль, benchmark runner;
- менеджер моделей (скачивание, SHA, место);
- автоподбор конфига под модель и устройство;
- UI и foreground service.

Граница проходит по строке «политика и память — наши, арифметика — ggml». Если для
политики не хватает хука в llama.cpp, добавляем минимальный патч и стараемся отправить
его upstream.

## Автоподбор под модель и устройство

Идея «выбрал модель — она сразу работает» реализуется не магией, а тремя шагами:

1. **Классификация.** Из GGUF читаем архитектуру, число слоёв/экспертов, типы тензоров,
   размер файла. Определяем: dense / MoE / ternary; какие тензоры GPU-совместимы.
2. **Оценка бюджета.** По устройству (memoryClass, availMem, UFS) и размеру dense/KV
   считаем, сколько остаётся на экспертный кэш. Если не влезает — уменьшаем ctx или
   предупреждаем.
3. **Короткая калибровка.** 20–30 секунд: prefill и decode на встроенном коротком
   промпте для 2–3 кандидатов (cpu / vulkan / opencl; 2/4/6 потоков; 2–3 размера кэша).
   Выбираем лучший и сохраняем профиль `model+device`.

Профиль — JSON рядом с моделью или в app files; пользователь может переопределить.
Калибровка не заменяет полноценный бенчмарк: она выбирает безопасные дефолты, а не
публикует рекорды.

## Открытые вопросы (решаются кодом и замером)

1. Vulkan или OpenCL на Adreno 630/750/830 — что стабильнее и быстрее.
2. Сколько слотов на слой оптимально на 6/16/24 GB.
3. Помогает ли GPU для decode на 845 или только для prefill.
4. Насколько page cache Android отдаёт под mmap модели.
5. Реальная цена `mmap` против `pread` на UFS 2.1.
6. Стоит ли держать dense на GPU на 6 GB.
7. Тернарные ядра: CPU достаточно или нужен GPU-кернел.
8. QNN на 845 — есть ли смысл (скорее нет).
