## 3. Clover: почему только 4838ffb

**Что сломано в mainline.** У `clover_moe` в mainline рекуррентный слой идёт по общему
Gated-DeltaNet-пути (`build_recurrent_attn`, только `ssm_conv1d`). В `4838ffb` тот же слой
вызывает `build_clover`, который использует четыре тензора на слой: `ssm_conv1d.weight_right`
(`[3,8192]`), `ssm_bd_logit_scale` (`[32]`), `ssm_bd_history.weight` и `.bias` (`[32]`). Это
30 слоёв × 4 = **120 тензоров**, ровно разница 853 − 733. Они меняют математику: правое
свёрточное окно, масштаб логитов и history-bias в softmax. Mainline с патчем загружает их как
`TENSOR_NOT_REQUIRED`, но не использует, поэтому текст бессвязный. Второй барьер — metadata:
наш файл не содержит `clover_moe.expert_shared_count`; mainline требует ключ, 4838ffb вообще
его не читает и выводит shared-эксперта из наличия тензоров. Патч добавляет дефолт 1.

**`llama_process` / `llama_batch_ext`.** В 4838ffb `llama_batch_ext` — расширенный батч:
несколько seq_id, токены или эмбеддинги, `embd_state` (MTP/deepstack), позиции на токен,
флаги output logits/embd. `llama_process(type, batch)` — тонкая обёртка:
`ENCODE → ctx->encode`, `DECODE → ctx->decode`. `llama_decode` внутри сам конвертирует
`llama_batch` в `llama_batch_ext` через `llama_batch_compat`, так что отдельной математики
нет. Для обычного AR достаточно `llama_process(DECODE, batch_ext)`; для block-diffusion нужен
`ENCODE` при `causal_attn=false` и маскированный токен `<|mask|>` (id 151669). Приложение
diffusion не включает.

**MoE-роутинг.** Router `ffn_gate_inp` F32 `[2048,256]` → логиты. В non-causal режиме
включается coreset: softmax, top-8, накопление массы по экспертам, отсечение по top_p=0.9 и
маска `+1e30/-1e30`. Далее top-8 с детерминированным tie-break по меньшему id (кастомный
`clover_sort_rows`), softmax-гейт и `build_moe_ffn` с SILU. Shared-эксперт считается всегда,
его гейт — сигмоида от скалярного произведения `cur · ffn_gate_inp_shexp`. В нескольких местах
применяется `build_bf16_round` — это влияет на побитовую воспроизводимость.

**I/O-профиль.** Эксперты: 10 804 527 104 B = 10 304 MiB, 40 слоёв × 256 экспертов; размер
эксперта 0.961 MiB (слои 16–37), 1.023 MiB (2–15), 1.195 MiB (0,1,38,39); среднее 1.006 MiB.
На токен читается 8/256: **337.6 MB (322 MiB)**. Не-экспертная часть — 1.74 GB (1 660 MiB):
output 398 MiB, token_embd 273 MiB, attn/ssm 842 MiB, shared 68 MiB, прочее 80 MiB. При
0.6 tok/s это 202 MB/s эффективного чтения, что совпадает с измеренным потолком UFS 2.1
(03: 265 MB/s в 1 поток, 531 MB/s в 2, 704 MB/s O_DIRECT). Page cache в idle держит 2.35 GiB
(19.6% файла); под inference на экспертов остаётся 1.7–1.9 GiB, hit rate 20–30%. Отсюда
предел: decode ≈ 337.6 MB / доступная полоса.

**Память.** Веса 11 975 MiB (mmap) + KV + recurrent state 62.8 MiB (измерено) + compute
127.5 MiB (batch 128). KV считается по 10 full-attention слоям, а не по 40:

| ctx | KV f16 | KV q8_0 | KV q4_0 |
|---:|---:|---:|---:|
| 2048 | 41.9 MB | 22.3 MB | 11.8 MB |
| 4096 | 83.9 MB | 44.6 MB | 23.6 MB |
| 32768 | 671 MB | 357 MB | 189 MB |
| 131072 | 2.68 GB | 1.43 GB | 755 MB |

Итого ctx4096/q8_0: ≈12 208 MiB (11.92 GiB); фактически PSS 2.98–3.97 GB, peak RSS 4.26 GB,
потому что file-backed страницы не резидентны целиком. На 6 GB: файл вдвое больше RAM, это
storage-bound демо; потолок ≈0.6–0.7 tok/s, при экспертном пуле ожидаемо 0.95–1.35 tok/s
(оценка 03). На 16 GB: 11.7 GiB может почти целиком лечь в page cache, тогда decode упирается
в compute; оценка 2–6 tok/s, **проверить** на Pad 2.

`sllm-cli check` для Clover даёт `est=12673 MB` и `E_RAM_LOW` при «доступно 8000 MB». Оценка
завышена: KV считается по 40 слоям (178 MB вместо 45) плюс фиксированные 528 MB. На 16 GB это
даст ложное предупреждение, если оставить `8000` жёстко.

## 4. Qwen 0.5B: baseline и daily driver

Файл 0.370 GiB, 24 слоя, 32k ctx, tied embeddings, простой ChatML-шаблон без thinking.
Измерено на MI 8 (4 потока, release): decode **25–27 tok/s**, prefill **42–48 tok/s**, TTFT
**1.3 s** на коротком промпте, PSS ~531 MB при ctx 4096. Она оставляет RAM на оболочку и
page cache, стартует за секунды и даёт предсказуемый поток. Поэтому она — эталон для
golden-тестов, проверки шаблона и UI, а не «умная модель»:
для сложных задач качество 0.5B недостаточно. BOS выключен (`add_bos=false`), EOS —
`<|im_end|>` 151645; шаблон при отсутствии system сам подставляет «You are Qwen…», поэтому
пустой system не нужен. Токенайзер BPE с pre `qwen2`; специальные токены —
CONTROL, поэтому при detokenize с `special=false` они подавляются.

## 5. Split GGUF

Правила llama.cpp: имена `prefix-00001-of-000NN.gguf`, пять цифр, нумерация с 1; метаданные
`split.no` (0-based), `split.count`, `split.tensors.count` (общее число тензоров на все шары).
Загрузчик открывает первый шар, сам строит список остальных и проверяет `split.no` каждого.
Валидация registry: все N файлов существуют; у каждого `split.count` совпадает; `split.no`
равен индексу; суммарный размер = сумма шар; `split.tensors.count` одинаков; только первый шар
попадает в список. Показывать одной карточкой: имя = prefix без суффикса, размер = сумма,
бейдж «3 шара». Ошибки: нет шара → `E_SPLIT_MISSING` (в enum его нет), выбран не
первый → `E_SPLIT_NOT_FIRST` (есть).

Текущий код читает только `split.count/no`, скрывает не-первые шары и **не проверяет наличие
остальных**; `estimate_mb` берёт размер только первого шара, то есть занижает вес модели.
SAF-импорт должен копировать все шары: URI не даёт `Range`, потоковое чтение шар невозможно.
Локальных split-моделей нет — «проверить» на синтетическом split Qwen через `llama-gguf-split`.

## 6. mmproj и vision

Признаки mmproj: `general.architecture = "clip"`, ключи `clip.*`, тензоры `mm.*`, `v.*`,
`a.*`; файл обычно называется `mmproj-*.gguf`. Ключевой признак vision —
`clip.has_vision_encoder = true`; `clip.has_audio_encoder = true` — это аудио, не vision.
`clip.projector_type` говорит, какой граф нужен (Qwen2-VL, Qwen2.5-VL, Gemma 3, Pixtral и т.д.).
Нельзя определять мультимодальность по наличию `clip.*` вообще: в текстовых GGUF иногда
лежат только параметры препроцессинга. Нужен именно boolean + `mm.*` тензоры.

Текущая логика `GgufMeta::is_mmproj()` ставит `has_clip` при **любом** ключе `clip.` — это
ложные срабатывания. Хуже: `preflight` возвращает `MmprojNotModel` до блока capabilities,
поэтому `Capability::Vision` там недостижим (мёртвый код). Vision должен вычисляться в
registry пары «base + mmproj», а не в preflight одного файла, и только если сборка линкует
mtmd (`LLAMA_BUILD_MTMD=ON`). Сейчас приложение текстовое, mtmd не линкуется: даже при
наличии mmproj кнопку image нужно держать disabled с причиной «движок собран без mtmd».
Если vision-тензоры лежат в одном файле с текстовой arch, llama-model-loader упадёт с
`wrong number of tensors`; preflight должен ловить префиксы `v.`/`mm.` и предупреждать
«single-file multimodal, нужен отдельный text-only GGUF».

- открытый `<think>` и `max_tokens=512` обрывают ответ до финального текста;
- Clover специальные токены имеют тип USER_DEFINED (4), а не CONTROL (3). В llama.cpp

  по EOS 248046;
- BOS принудительно не добавляется; для Qwen/Clover это совпадает с metadata, для Gemma/
  Mistral-подобных моделей — потенциальная тихая деградация, проверять отдельно.

## 9. Рекомендации registry / engine / UI

**Статусы.** `Discovered → Preflighted → Compatible/Incompatible → Loading → Ready →
Generating/Trimming`; ошибки — отдельное состояние с кодом, не «Ready». `Ready` — только после
успешного preflight и загрузки; одновременно одна тяжёлая модель.

**Бейджи.** Arch; реальный квант (для Clover «IQ3_XXS/IQ2_S mix», не «Q4_0»); размер;
`MoE 256e/8a`; `4838ffb-only`; `text`; `vision` только при mmproj + mtmd; `3 shards`;
`chat template` / `ChatML fallback`; `BOS off`. Clover — «demo / storage-bound», не
«recommended».

**Fit.** Считать `weights + KV + RS + compute + LoRA + mmproj`; `available_mb` брать из
Android `MemoryInfo`, не константу 8000. Уровни: `Comfort` (оценка ≤ 0.55 × avail),
`Tight` (≤ avail − reserve), `Mmap` (веса > avail, но есть место на storage; предупредить,
что скорость = I/O), `No` (нет места). Для Clover на 6 GB — `Mmap`, ожидание «≈0.6 tok/s,
проверить»; на 16 GB — `Tight/Mmap`, «2–6 tok/s, проверить».

**Предупреждения.** `W_QUANT_LABEL_MISMATCH` (ftype ≠ состав), `W_MIXED_QUANT`,
`W_TEMPLATE_FALLBACK`, `W_THINK_OPEN` (Clover), `W_BOS_DISABLED`, `W_MMPROJ_WITHOUT_MTMD`,
`W_VISION_TOKENS_TEXT_ONLY`, `W_SPLIT_UNVERIFIED`, `W_MOE_STORAGE_BOUND`, `W_CTX_CLAMPED`,
`W_FLAVOR_REQUIRED` (clover_moe → только 4838ffb). В деталях — формула памяти и первые 3 типа
тензоров с долями.

## Пять ключевых выводов

1. **`file_type` нельзя считать квантом.** У Clover там Q4_0 при 82% IQ2/IQ3; у Qwen
   «Q4_K_M» — рецепт с 44% Q5_0 и 37% Q8_0. Registry обязан показывать состав по байтам.
2. **Clover работает только на 4838ffb** не из-за одной архитектуры, а из-за математики
   30 рекуррентных слоёв: `weight_right`, `bd_logit_scale`, `bd_history` (120 тензоров) и
   отсутствующего `expert_shared_count`. Mainline с патчем грузит, но считает иначе.
3. **Предел Clover на 6 GB — I/O, а не CPU.** 337.6 MB экспертов на токен при ~200 MB/s дают
   0.6 tok/s; на 16 GB вес влезает в page cache, и только там начинается compute-предел
   (2–6 tok/s, проверить).
4. **Preflight уже даёт правильный код для PTQ**, но таблица типов эвристическая и разрешает
   мусорные id; её нужно генерировать из заголовков конкретного дерева. Для split не хватает
   проверки шар и суммарного размера, для vision — пары base+mmproj и mtmd.
5. **Qwen 0.5B — эталон, а не замена рассуждению.** 25–27 tok/s, TTFT 1.3 s, 531 MB PSS:
   он держит golden-тесты, шаблон и UI, пока Clover остаётся демо и полигоном I/O-кэша.
